Google Photos — AI-Powered Discovery Engine
Detailed Product Problem Statement:
Project Context
You are a Product Manager on the Core Experience team at Google Photos.
Over years of usage, people accumulate thousands of photos, videos, screenshots, documents, receipts, notes, tickets, medical information, travel memories, family moments, and other visual records in Google Photos.
Finding a recent or precisely described item can be relatively straightforward when the user knows what to search for.
However, retrieval becomes significantly harder when the user's memory is incomplete.
A user may remember the experience, context, people, object, or purpose associated with a photo without remembering the exact metadata needed to retrieve it.
For example:
"That small café we went to during our Goa trip."
"The picture of the medicine I took when I was sick last year."
"The screenshot of that flight ticket I booked."
"The photo of the dress I wanted to buy."
"The picture from my cousin's wedding where we were all standing together."
"That document I photographed a few months ago."
In each case, the user may be confident that the photo exists while being unable to remember:
•	When it was taken
•	Where it was taken
•	The exact words visible in the image
•	Which album it belongs to
•	Who else appears in it
•	What the object was called
•	Whether it was a photo, screenshot, scanned document, or video
•	The exact phrase that would retrieve it through search
This creates a gap between human memory and machine retrieval.
________________________________________
1. Business Objective
One of Google Photos' strategic goals is:
Increase the percentage of users who successfully retrieve a photo they remember but cannot precisely describe when they begin searching.
The goal is not to improve search in general.
The focus is specifically on:
Memory-driven retrieval where the user knows the item exists but cannot precisely specify the information needed to find it.
The product team needs to understand where this retrieval experience breaks down and why before proposing a solution.
________________________________________
2. Core Product Problem
The team currently understands the desired outcome:
User remembers something → User tries to retrieve it → User may fail to find it.
However, the underlying problems are not sufficiently understood.
We do not yet know:
•	What kinds of visual memories users most commonly struggle to retrieve.
•	What information users remember when trying to retrieve old photos.
•	What information they tend to forget.
•	How people describe memories when they cannot recall exact metadata.
•	How users translate memories into search queries.
•	What happens when the first query fails.
•	How users reformulate searches.
•	Whether users rely on trial-and-error.
•	Whether they leave Google Photos and use other sources or external methods.
•	Whether users browse albums, dates, locations, people, or other organizational structures instead of searching.
•	Which retrieval problems are widespread versus niche.
•	Which problems are caused by missing user memory versus limitations in the retrieval experience.
•	Whether different user segments experience fundamentally different retrieval barriers.
•	Which problems represent meaningful opportunities to improve successful retrieval.
Therefore, the first challenge is problem discovery, not feature development.
________________________________________
3. Primary Problem Statement
Formal Problem Statement
Google Photos users often remember visual information as experiences, contexts, relationships, objects, or purposes rather than as precise searchable attributes. When attempting to retrieve old photos or other visual memories, this incomplete or differently structured memory can make it difficult to formulate an effective search or navigate to the correct item.
Although users publicly discuss these retrieval difficulties across app reviews, community discussions, Reddit, social platforms, YouTube comments, forums, and other sources, these conversations are unstructured, fragmented, and difficult to analyze systematically at scale.
The product team therefore lacks an evidence-backed understanding of the distinct retrieval problems users experience, how users remember and describe those memories, where retrieval breaks down, which user segments are affected, and which opportunity areas could most meaningfully improve successful retrieval.
The challenge is to build an AI-Powered Discovery Engine that analyzes real user conversations at scale and converts them into a structured, traceable, evidence-backed map of retrieval problems and opportunity areas—without inventing, assuming, or overstating evidence at any stage.

11. Research Question E — Where Does Retrieval Break Down?
The discovery engine should identify the specific failure point in the user's journey.
Possible stages:
Stage 1 — Memory Formation
The user remembers an experience or visual object.
Stage 2 — Retrieval Trigger
The user suddenly needs the old item.
Stage 3 — Search Formulation
The user attempts to translate memory into a searchable description.
Stage 4 — First Retrieval Attempt
The user performs a search.
Stage 5 — Result Evaluation
The user examines results.
Stage 6 — Search Reformulation
The user changes keywords or search strategy.
Stage 7 — Navigation / Browsing
The user attempts another retrieval method.
Stage 8 — Abandonment
The user gives up or uses another source.
The engine should identify where problems most frequently occur.

12. Research Question F — What Happens After a Failed Search?
This is particularly important.
A failed first search does not necessarily mean the user immediately abandons the task.
The user may:
•	Try another query.
•	Add a remembered attribute.
•	Remove a keyword.
•	Search a person.
•	Search a place.
•	Search a date range.
•	Browse an album.
•	Scroll chronologically.
•	Search externally.
•	Ask another person.
•	Give up.
The system should discover these recovery behaviors from real conversations.

13. Research Question G — What Are the Distinct Retrieval Problems?
The AI system must identify problem clusters, not merely topics.
For example, these are different:
Problem A — Forgotten Date
User remembers the event but not when it happened.
Problem B — Forgotten Entity Name
User remembers a café/restaurant/person/object but not its name.
Problem C — Context-Heavy Memory
User remembers the situation or experience rather than a searchable object.
Problem D — Information-Dense Image
User remembers information contained within the image but not the filename or date.
Problem E — Ambiguous Visual Memory
User remembers the image visually but lacks a unique identifier.
Problem F — Search Reformulation Failure
User knows approximately what they remember but cannot discover the query that retrieves it.
Problem G — Result Overload
The target exists among many visually similar results and is difficult to identify.
These must be treated as candidate problem hypotheses until supported by evidence.

14. Discovery Must Go Beyond Sentiment Analysis
A core requirement of this project is:
Sentiment analysis is not the objective.
The engine should not stop at:
40% negative
35% positive
25% neutral
Similarly, it should not stop at:
"Users complain about search."
Instead, it should transform raw evidence into:
Conversation → User context → Behavior → Problem → Need → Opportunity
For example:
Raw Evidence
User states that they remember a photo from a particular trip but cannot remember the date and cannot locate it through search.
Structured Interpretation
Memory: Trip context
Missing information: Exact date
Retrieval attempt: Search
Barrier: Date uncertainty
Outcome: Retrieval difficulty
Problem Hypothesis
Users may struggle when their strongest memory representation is contextual rather than metadata-oriented.
Opportunity Hypothesis
There may be an opportunity to support context-based retrieval.
However:
The opportunity hypothesis must never be presented as a confirmed user need unless the evidence supports it.

15. Evidence-First Architecture
The engine should treat every AI-generated insight as a claim that requires evidence.

Source → Conversation → Extracted Evidence → Pattern → Problem → Opportunity
Every higher-level conclusion must be traceable backward through this chain.

•	Assigning unsupported demographics.

18. No Evidence = No Claim
The system should follow a strict rule:
If the evidence does not support a claim, the system must not make the claim.
Instead, it should say:
•	"Insufficient evidence"
•	"Evidence is limited"
•	"Observed in a small number of sources"
•	"Hypothesis requiring validation"
•	"No reliable evidence found"
This behavior is preferable to producing a confident-looking answer.
________________________________________
19. No Fabricated Quantification
The system must never produce:
"63% of users have this problem"
unless there is a clearly documented denominator and methodology supporting that figure.
The engine must distinguish among:
Measured
Directly calculated from the collected dataset.
Estimated
Derived using a documented methodology.
Observed
A pattern seen in the collected evidence but not statistically representative.
Hypothesized
A possible interpretation that still requires validation.
These labels should be visible in the output.
________________________________________
20. Quote Integrity
If the system displays a user quote:
The quote must exist in the underlying retrieved source.
The engine should store:
•	Exact quote
•	Source
•	URL/identifier
•	Surrounding context
•	Retrieval date
AI should not rewrite a quote and present the rewritten version as verbatim user language.
Summaries may be generated, but they must be explicitly labeled as:
AI-generated summary
________________________________________
21. Source Reliability Hierarchy
Not all evidence should be treated equally.
The engine should preserve source type and distinguish:
Direct User Evidence
Actual review or user-generated discussion.
Community Discussion
Multiple users discussing a shared experience.
Secondary Interpretation
A third party describing user behavior.
AI Inference
An interpretation generated from available evidence.
The system should never merge these categories without labeling them.
________________________________________
22. Evidence Deduplication
The same underlying complaint may appear:
•	On multiple websites.
•	In reposts.
•	In quoted discussions.
•	Across syndicated content.
The engine should attempt to detect duplicate or near-duplicate evidence.
Otherwise, one original comment could incorrectly appear to represent dozens of independent users.
Therefore:
Independent evidence count should be separated from raw mention count.

27. Opportunity Comparison
This is one of the most important requirements.
The engine must not simply generate a list of problems.
It should enable the PM to compare opportunity areas.
For each opportunity, assess evidence-based dimensions such as:
1. Problem Prevalence
How frequently does the problem appear in the collected evidence?
2. Retrieval Relevance
How directly does the problem affect the task of finding an existing visual memory?
3. User Impact
How severe does the retrieval difficulty appear to be?
4. Evidence Strength
How consistently is the problem supported?
5. Cross-Source Validation
Does it appear across independent sources?
6. Segment Reach
How many identifiable user groups appear affected?
7. Conversion-to-Retrieval Relevance
Would solving the issue plausibly improve successful retrieval?
This should be framed as a prioritization hypothesis, not as proof of causal impact.
________________________________________
28. Opportunity Scoring
A scoring framework may be introduced to make comparison systematic.
For example:
Opportunity Score = Prevalence × Impact × Evidence Strength × Retrieval Relevance
However, the exact scoring formula should be:
•	Explicit
•	Configurable
•	Visible to the user
•	Supported by underlying evidence
•	Separated from factual observations
The system must not make a score appear scientifically objective when the underlying weights are subjective.
For example:
Evidence Score: 82/100
should never be presented without explaining:
•	What the 82 means.
•	How it was calculated.
•	Which evidence contributed.
•	Which dimensions are subjective.

29. Evidence vs Interpretation Model
Every insight should be separated into four layers.
Layer 1 — Evidence
What the user actually said.
Layer 2 — Pattern
What is repeatedly observed across evidence.
Layer 3 — Problem Hypothesis
What underlying problem may explain the pattern.
Layer 4 — Opportunity Hypothesis
What product opportunity could potentially address the problem.
Example:
Evidence
Users describe remembering a trip but forgetting the exact date.
↓
Pattern
Several conversations describe retrieval difficulty under forgotten-date conditions.
↓
Problem Hypothesis
Users may rely more strongly on contextual memories than exact temporal metadata.
↓
Opportunity Hypothesis
A retrieval experience could potentially leverage contextual temporal cues.
This separation should be visible in the application.

34. Hallucination Guardrails
The implementation should include explicit guardrails.
Guardrail 1 — Citation Mandatory
Analytical claims require supporting evidence.
Guardrail 2 — Citation Validation
The cited evidence must actually support the claim.
Guardrail 3 — No Source, No Claim
Unsupported claims must be rejected or downgraded to hypotheses.
Guardrail 4 — Exact Quote Verification
Quoted text must match source text.
Guardrail 5 — No Fake Statistics
Numbers must originate from computation over the actual dataset.
Guardrail 6 — Uncertainty Labels
The system must expose uncertainty.
Guardrail 7 — Source-Level Traceability
Every insight must lead back to source material.
Guardrail 8 — Independent Evidence Detection
Repeated copies must not be counted as independent users.
Guardrail 9 — Temporal Awareness
The source date must be preserved whenever available.
Guardrail 10 — Model Knowledge Isolation
The LLM must not silently substitute general knowledge for missing evidence.

35. Failure Behavior
The engine should be intentionally conservative.
When it cannot answer confidently, it should say:
"The available evidence is insufficient to establish this pattern."
When it finds only a small number of examples:
"This pattern appears in a limited number of collected conversations and should not yet be treated as a widespread problem."
When evidence conflicts:
"The evidence is mixed. Some conversations indicate X, while others indicate Y."
When a conclusion is an interpretation:
"Hypothesis based on the observed evidence."
This is a core product behavior, not an error condition.

36. What the Engine Should NOT Do
The discovery engine should not:
•	Invent user research.
•	Invent interviews.
•	Invent statistics.
•	Invent quotes.
•	Invent sources.
•	Use synthetic reviews as evidence.
•	Treat AI-generated examples as real users.
•	Assume the user problem before analysis.
•	Start with a feature and work backward.
•	Treat sentiment as the primary insight.
•	Equate complaint frequency with business impact.
•	Assume causation from correlation.
•	Produce arbitrary opportunity scores.
•	Hide uncertainty.
•	Present model knowledge as research evidence.

42. Core Product Philosophy
The project should follow one principle throughout:
Do not ask the AI "What feature should Google Photos build?"
Ask:
"What are users actually struggling to retrieve, how do we know, how widespread is the problem, and what evidence suggests it is worth solving?"
Only after that discovery work should the Product Manager move into:
Problem Validation → Opportunity Definition → Solution Discovery → Prototyping → Experimentation
