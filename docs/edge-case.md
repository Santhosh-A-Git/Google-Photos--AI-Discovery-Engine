# AI-Powered Discovery Engine — Comprehensive Edge Cases & Corner Scenarios

This document outlines an exhaustive list of end-to-end corner scenarios that the AI-Powered Discovery Engine might encounter across its entire lifecycle. Addressing these ensures the system remains robust, trustworthy, and strictly compliant with the anti-hallucination and evidence-first constraints.

---

## 1. Data Ingestion & Source Anomalies

### 1.1. Sarcasm and Irony
- **Scenario:** Users expressing frustration using sarcasm (e.g., *"I absolutely love how Google Photos completely hides my screenshots from last year."*).
- **Risk:** The LLM interprets the sentiment as positive or misunderstands the core complaint.
- **Mitigation:** Prompt the extraction LLM to specifically analyze the *action* and *outcome* (user attempted retrieval, retrieval failed) rather than tone.

### 1.2. Cross-Language and Mixed-Language Queries
- **Scenario:** A user posts mixing English and a local language (e.g., *"Can't find the photo from my cousin's shaadi."*).
- **Risk:** The engine drops the context ("shaadi" = wedding) or discards non-English reviews entirely.
- **Mitigation:** Use a multi-lingual LLM for extraction, mapping local colloquialisms to standard memory taxonomy (e.g., "shaadi" -> "Wedding/Event").

### 1.3. Buried Complaints (Extremely Long Rants)
- **Scenario:** A 500-word post on Reddit complaining about Google's ecosystem, with only one sentence dedicated to a photo retrieval failure.
- **Risk:** The embedding model dilutes the semantic weight of the retrieval complaint due to the surrounding noise.
- **Mitigation:** Introduce a pre-processing chunking step that extracts only sentences containing retrieval-related keywords before passing them to the Vector DB.

### 1.4. Personally Identifiable Information (PII) Leakage
- **Scenario:** A user's public review accidentally includes their real phone number, email, or full name when describing a lost photo.
- **Risk:** The engine ingests, stores, and potentially displays PII on the PM dashboard.
- **Mitigation:** Implement a strict regex/PII-scrubbing filter in the ingestion pipeline before data hits the storage layer.

### 1.5. Bot & AI-Generated Spam Reviews
- **Scenario:** Synthetic reviews generated by bots to manipulate App Store ratings that coincidentally mention "search".
- **Risk:** Pollutes the dataset with fake evidence.
- **Mitigation:** Implement heuristic spam filters during ingestion (e.g., identifying repetitive structures, low account karma on Reddit, or generic phrasing).

## 2. Processing, Storage & Deduplication

### 2.1. The "Echo Chamber" Effect (Syndicated Content)
- **Scenario:** A popular tech blog writes an article quoting a single Reddit complaint. 15 other blogs copy that article.
- **Risk:** The engine counts this as 16 independent sources and artificially inflates "Evidence Volume."
- **Mitigation:** Deduplication must compare *source types*. Secondary interpretations (blogs) should not increase the independent user count.

### 2.2. Multi-Platform Cross-Posting
- **Scenario:** A highly frustrated user posts the exact same complaint on the Play Store, Reddit, and a Help Community.
- **Risk:** Inflated independent evidence count for a single user's isolated issue.
- **Mitigation:** Implement cross-platform fuzzy matching. If identical phrasing appears across platforms within a 48-hour window, cluster them as a single user incident.

### 2.3. Temporal Drift of Complaints
- **Scenario:** A user complains about a missing photo. Three months later, they post again saying, *"Still can't find that photo."*
- **Risk:** The system counts this as two independent users.
- **Mitigation:** If the username/ID matches across the same platform with the same semantic issue, merge the evidence under a single user journey.

## 3. LLM Extraction & Inference Edge Cases

### 3.1. Competitive Benchmarking (False Positives)
- **Scenario:** User writes: *"Apple Photos let me find my dog immediately by searching 'terrier', but Google Photos just showed me a bunch of cats."*
- **Risk:** The LLM extracts "Apple Photos" as the target platform or misunderstands the retrieval attempt.
- **Mitigation:** The extraction prompt must explicitly ask the LLM to separate the target platform from comparative platforms.

### 3.2. Backend Indexing Failure vs. Memory Failure
- **Scenario:** The user searches exactly what is in the photo (e.g., "Receipt"), and the photo clearly says "Receipt", but it's blurry and Google Photos OCR failed to index it.
- **Risk:** The system categorizes this as a user memory problem (e.g., "Forgotten metadata") when the user actually remembered perfectly—the backend OCR simply failed.
- **Mitigation:** Train the LLM to identify when a user explicitly states the query *should* have worked based on visible image content. Label this as "Indexing/OCR Barrier", not a "Memory Barrier."

### 3.3. Result Overload vs. True Retrieval Failure
- **Scenario:** The user remembers the exact date and location. The search works perfectly, returning 2,000 photos, but the user gives up scrolling.
- **Risk:** Flagged as "Forgotten Context" instead of a filtering/UI issue.
- **Mitigation:** Journey mapping must clearly distinguish between *Query Formulation Failure* (couldn't search) and *Result Evaluation Failure* (searched successfully, but couldn't isolate the target).

### 3.4. Vague Memory Constraints
- **Scenario:** User states: *"I know I took a picture of it, but I can't find it."*
- **Risk:** The LLM hallucinates what "it" is.
- **Mitigation:** Categorize as `Insufficient Context`. No evidence = No claim.

### 3.5. Formatting/Output Breakdown
- **Scenario:** The Groq LLM outputs malformed JSON or includes conversational text (e.g., "Here is the extraction...") instead of the required schema.
- **Risk:** The pipeline crashes during parsing.
- **Mitigation:** Enforce strict JSON-mode in the LLM API call and implement a robust retry logic with a fallback parser.

## 4. Guardrail & Verification Edge Cases

### 4.1. "Cleaned up" Quotes Failing Integrity Checks
- **Scenario:** A user writes *"im tryin to find dat pic"*. The LLM extracts the quote but auto-corrects it to *"I'm trying to find that pic"*.
- **Risk:** The strict string-matching Quote Integrity Checker rejects a valid insight because the LLM fixed the grammar.
- **Mitigation:** Use a high-threshold similarity algorithm (e.g., Levenshtein distance) instead of strict `==` matching, allowing for minor grammar corrections while blocking fabricated words.

### 4.2. Hallucinated Source URLs
- **Scenario:** The LLM tries to satisfy the citation requirement by inventing a plausible-looking Reddit URL (e.g., `reddit.com/r/googlephotos/comments/fake_id`).
- **Risk:** A PM clicks the link and hits a 404, eroding trust in the entire tool.
- **Mitigation:** The pipeline must *never* allow the LLM to generate URLs. The LLM only returns the Database ID, and the application layer attaches the hardcoded URL from the database.

### 4.3. Contradictory Evidence Within a Cluster
- **Scenario:** Within a "Location-based search" cluster, 50% of users say the location search is too broad, and 50% say it's too strict.
- **Risk:** The engine averages this out to "Location search is broken", losing critical nuance.
- **Mitigation:** Instruct the clustering prompt to flag *contradictions* within a cluster. The dashboard highlights these as "Polarized Feedback."

### 4.4. RAG Context Window Overflow
- **Scenario:** The PM asks the dashboard a broad question: *"Summarize all complaints about screenshots."* There are 15,000 matching evidence items.
- **Risk:** The query exceeds the LLM's context window, causing a crash or truncation of critical data.
- **Mitigation:** Implement Map-Reduce summarization for large queries, or restrict RAG context to the top 50 most representative/diverse embedded chunks.

## 5. Presentation & Exploration (Dashboard) Edge Cases

### 5.1. Data Skew from Viral Threads
- **Scenario:** A single Reddit thread complaining about finding old pets goes viral, generating 5,000 "Me too!" comments. 
- **Risk:** The Opportunity Matrix ranks "Pet Photo Retrieval" as a 100x larger problem than "Document Retrieval" purely due to viral amplification of a single thread.
- **Mitigation:** Cap the weight of a single root source (thread). The dashboard should visualize both *Thread Volume* and *Independent Occurrences*.

### 5.2. The "Low-Confidence Flood"
- **Scenario:** The engine discovers 200 highly specific but isolated edge-case problems (e.g., 1 user complaining about a specific 1980s car model).
- **Risk:** The Discovery Dashboard matrix becomes cluttered, burying the high-impact problems.
- **Mitigation:** Enforce a baseline threshold (e.g., Minimum 5 independent sources) before a cluster is promoted to the primary PM dashboard view. Keep others in a "Noise/Unvalidated" bucket.

### 5.3. Cold Start / Empty State
- **Scenario:** The PM opens the dashboard on day 1, before enough evidence has crossed the confidence threshold.
- **Risk:** The dashboard displays broken charts or says "No Problems Found."
- **Mitigation:** Design clear "Gathering Evidence..." empty states that show ingestion progress and raw feed previews to build trust while clustering is ongoing.
